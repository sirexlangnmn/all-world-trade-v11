# 2. Objective

Make the server the only authority for password hashing during password reset, and guarantee that the password-reset path can never store a client-supplied value verbatim.

The expected end state is:

- A user submits a new password through the existing reset page.
- The server receives the plaintext over the existing form POST, validates it, hashes it with bcrypt (cost 12, unique salt), and writes only the hash to `users_accounts.password`.
- A direct `curl` POST containing a plaintext password results in a stored bcrypt hash — never plaintext, never an empty value.
- A direct POST containing only the legacy `password3` field cannot write that value.
- An old cached browser tab that still sends both `password` (plaintext) and `password3` (pre-hashed) continues to work, because the server hashes `password` and ignores `password3`.
- The password-reset page no longer depends on the public bcrypt oracle `POST /api/post/password-hashing`.
- The user-visible flow is unchanged: same URL, same success string, same redirect, same login behaviour.

Out of scope: registration hashing (Finding 47), the public hashing/comparison endpoints (Finding 48), JWT removal (Finding 4), reset-token invalidation/expiry (Findings 19/23/49), rate limiting (Finding 51), and the forgot-password response leak (Finding 50). Report those; do not silently fix them in this task.

# 3. Problem / Finding

## Vulnerability type

- **Cleartext storage of a sensitive credential** — CWE-256 (Plaintext Storage of a Password), OWASP A02:2021 Cryptographic Failures.
- **Severity:** CRITICAL / HIGH in `CODE_REVIEW.md`.
- **Attack surface:** `POST /reset-password/:token` — public, reachable by anyone holding a reset token (or by anyone who can obtain one). No authentication is required beyond the token.
- **Affected functionality:** password reset and every subsequent login for that account.

## What `CODE_REVIEW.md` reported

The reset route read the hidden client-generated field `password3` and passed it directly to the update query:

```js
const inputObject = {
    password: password3,
};

db.query(USERS_ACCOUNTS.UPDATE_PASSWORD, [...Object.values(inputObject), UUID], function (err, result) {
    // ...
});
```

`UPDATE_PASSWORD` is parameterized (`app/query/users_accounts.query.js:26-28`), so this is **not** an SQL injection finding. The problem is that the value itself is stored verbatim.

## Verified current state (do not overstate or understate)

At the time of writing, the working tree contains the candidate fix. The original defect still exists at `HEAD` (`git show HEAD:app/routes/forgot-password.js`). The following facts were verified by reading the working tree:

1. **The server now reads the plaintext field.** `app/routes/forgot-password.js:189-212` destructures `{ password, password2 } = req.body`, calls `passwordResetService.setNewPassword(...)`, and returns the exact string `'reset password successfully'`.
2. **Hashing is server-side.** `app/services/password-reset.service.js` validates the input, rejects strings over bcrypt's 72-byte limit, hashes with `bcrypt.hash(password, 12)`, and updates only the `password` column with `{ silent: true }`.
3. **The client no longer pre-hashes.** `public/assets/js/reset-password.js` no longer defines `password3` or calls `/api/post/password-hashing`.
4. **The hidden `password3` input still exists** in `public/view/reset-password/index.ejs:75-85`. It is unused by the new server and new client. It is deliberately retained for one release so an old cached client does not throw when it tries to populate it.
5. **The public oracle still exists.** `app/routes/password.js:4-16` hashes with cost **10**, not 12, and remains publicly reachable. Registration still depends on it. This is Finding 48, not this task.
6. **Registration still trusts client-supplied hashes.** Examples: `app/db_controllers/registration_v2.controller.js:78` (`hashedPassword`), `small-scale-company-registration.controller.js:71`, `medium-scale-company-registration.controller.js:70`, `large-scale-company-registration.controller.js:71`, `trader-scale-company-registration.controller.js:65,263`, `help-and-support.controller.js:54`. This is Finding 47, not this task.
7. **Non-bcrypt rows may still exist.** `CODE_REVIEW.md` Finding 46 records 4 non-bcrypt passwords found in an audit. `app/services/auth.service.js:32-41` catches bcrypt comparison errors and returns `false`, so those accounts cannot log in until they reset. This task must audit and report them; it must not silently rewrite them.
8. **Tests pass.** `node --test test/password-reset.test.js` reports 13 passing tests. `npm test` is intentionally a failing stub and must not be “fixed” here.

**Therefore the finding is:** the server must never accept a client-supplied value as the final stored password. The candidate implementation satisfies this, but the task is not complete until the implementation is verified against the database/runtime and the remaining legacy data is assessed.

## Why a naive fix is wrong

Do **not** simply add this while leaving the client unchanged:

```js
const hashedPassword = await bcrypt.hash(password3, 12);
```

In the normal browser flow (old client), `password3` is already a bcrypt hash (cost 10). Hashing it again stores a **hash of a hash**; the user's plaintext then will not match at login and the account is locked out.

The client pre-hashing and the server update must be changed together, and the server must read the plaintext field — not the pre-hashed field.

# 4. Affected Functionality

**Feature:** password reset via an emailed token.

```text
public/view/reset-password/index.ejs
   ↓ user types "password" / "password2"
public/assets/js/reset-password.js
   ├─ (old) keyup → POST /api/post/password-hashing → hidden password3
   └─ submit → jQuery serialize() → POST /reset-password/:token
                    fields: password, password2, (legacy password3)
   ↓
app/routes/forgot-password.js
   POST /reset-password/:token
   ├─ Reset_tokens.findOne({ token })                    (Sequelize)
   ├─ Users_accounts.findOne({ uuid: resetToken.uuid })  (Sequelize)
   ├─ passwordResetService.setNewPassword(uuid, { password, password2 })
   │     ├─ assertPassword (non-empty string, <= 72 UTF-8 bytes)
   │     ├─ assertPasswordConfirmation (when password2 is present)
   │     └─ bcrypt.hash(password, 12)
   └─ Users_accounts.update({ password: hash }, { where: { uuid }, silent: true })
   ↓
users_accounts.password  (bcrypt cost-12 hash only)
   ↓
login: app/services/auth.service.js → verifyPassword → bcrypt.compare(plaintext, stored)
```

**Consumers that must keep working:**

- `public/assets/js/reset-password.js:22-31` compares the response with the **exact string** `'reset password successfully'` and redirects to `/login` after 3 seconds. Any other string shows a warning.
- `app/services/auth.service.js:32-41` verifies with `bcrypt.compare`; it tolerates non-bcrypt stored values by returning `false` instead of throwing.
- `app/services/auth.service.js:13-18` documents that existing hashes are cost 10. bcrypt compares cost-10 and cost-12 hashes without issue; no login change is needed.
- `app/db_models/users_accounts.model.js` defines `password` as `Sequelize.STRING`, which is wide enough for a 60-character bcrypt hash.
- `README.md` §12.2 claims bcrypt with 12 rounds. After this fix, reset passwords actually use 12; existing hashes remain valid at their original cost.

**Not in scope (report only):**

- `app/models/forgot-password.model.js` returns the stored password hash to the browser (Finding 50).
- `app/routes/forgot-password.js:46-95` creates an unused JWT that embeds the password/hash (Finding 4).
- `app/routes/forgot-password.js:166-187` and `:189-212` dereference `resetToken.uuid` and `userAccount.uuid` without null or expiry checks (Findings 19/49).
- `app/routes/forgot-password.js` never deletes the reset token after use (Findings 23/49).
- `app/routes/password.js` is a public bcrypt hash/compare oracle (Findings 5/48). Registration still uses it; do not remove it here.
- Registration controllers trust a client-supplied `hashedPassword` (Finding 47). Do not expand this task into the registration stack.
- Reset endpoints have no rate limiting (Finding 51).

### Service — `app/services/password-reset.service.js`

```js
const bcrypt = require('bcrypt');

const db = require('../db_models');

const PASSWORD_HASH_ROUNDS = 12;
const MAX_PASSWORD_BYTES = 72;

function assertPassword(password) {
    if (typeof password !== 'string' || password.length === 0) {
        throw new TypeError('Password must be a non-empty string');
    }

    if (Buffer.byteLength(password, 'utf8') > MAX_PASSWORD_BYTES) {
        throw new TypeError(`Password must not exceed ${MAX_PASSWORD_BYTES} bytes`);
    }
}

function assertPasswordConfirmation(password, password2) {
    if (password2 !== undefined && password2 !== null && password2 !== password) {
        throw new TypeError('Password confirmation does not match');
    }
}

async function hashPassword(password) {
    assertPassword(password);

    return bcrypt.hash(password, PASSWORD_HASH_ROUNDS);
}

class PasswordResetService {
    constructor(dbRef = db) {
        this.UsersAccounts = dbRef.users_accounts;
    }

    async setNewPassword(uuid, { password, password2 } = {}) {
        if (typeof uuid !== 'string' || uuid.length === 0) {
            throw new TypeError('A user UUID is required');
        }

        assertPasswordConfirmation(password, password2);

        const hashedPassword = await hashPassword(password);

        await this.UsersAccounts.update({ password: hashedPassword }, { where: { uuid }, silent: true });
    }
}
```

Key properties:

- Validation happens **before** bcrypt.
- The hash is never returned to the caller.
- `password3` is never read.
- Only the `password` column is written.
- `silent: true` preserves the old raw-SQL behaviour of not touching `updatedAt`.

# 8. Current → Target

## Current (the defect)

```text
Browser types password
   ↓ keyup
POST /api/post/password-hashing → bcrypt hash (cost 10)
   ↓
hidden password3 = hash
   ↓ submit (password, password2, password3)
Server reads password3 and stores it verbatim.
```

## Target

```text
Browser types password
   ↓ submit (password, password2; password3 may still be present from cached JS)
Server reads the plaintext "password" field, ignores "password3"
   ↓
validate: non-empty string, UTF-8 length <= 72 bytes, confirmation matches when supplied
   ↓
bcrypt.hash(password, 12) → unique-salted hash
   ↓
Users_accounts.update({ password: hash }, { where: { uuid }, silent: true })
   ↓
response: "reset password successfully"   (unchanged)
```

## Before / after

**Before (`HEAD`):**

```js
const { password3 } = req.body;
const inputObject = { password: password3 };
db.query(USERS_ACCOUNTS.UPDATE_PASSWORD, [...Object.values(inputObject), UUID], (err, result) => {
    // ...
});
```

**After (target, already present in the candidate tree):**

```js
const { password, password2 } = req.body;

await passwordResetService.setNewPassword(userAccount.uuid, { password, password2 });

return res.send('reset password successfully');
```

**Client target:**

```js
// No password3, no /api/post/password-hashing call.
function forgotPasswordSubmitHandler(e) {
    e.preventDefault();

    if (password1.value !== password2.value) {
        Swal.fire('Warning', 'Confirm Password Failed', 'warning');
        return;
    }

    $.ajax({
        url: window.location.href,
        type: 'POST',
        data: resetPasswordForm.serialize(),
        // success handler unchanged
    });
}
```

## Key contract decision

The server reads the existing visible field name **`password`**, not the hidden `password3`. This is deliberate:

- New client: sends `password` (plaintext) and `password2`.
- Old cached client: also sends `password` (plaintext), plus a hash in `password3`. The server ignores `password3`, so no double hash occurs.
- There is **no bcrypt-shaped-input detection branch** and no “trust this hash if it looks like a hash” path. Server-side hashing is the only path.
- The success string remains byte-identical.

**Do not “improve” this by hashing `password3` when it exists.** That reintroduces the double-hash bug for old clients and re-establishes trust in a client-controlled value.

# 11. Security Requirements

Required:

- The server must generate the hash. Never store a value received from the client as the final password.
- Use bcrypt with a per-password salt (bcrypt does this automatically).
- Use **12 rounds** to match `CODE_REVIEW.md` Finding 3 and `README.md` §12.2.
- Existing cost-10 hashes remain valid and do not need to be rehashed during login.
- Validate that `password` is a non-empty string before hashing.
- Reject values over 72 UTF-8 bytes explicitly; do not silently truncate.
- If `password2` is supplied, require it to equal `password`.
- Keep the query parameterized. Never interpolate the hash, UUID, or password into SQL.
- Never log the plaintext password, the hash, or the full request body.
- Never return the password or hash in the response.
- Never send the stored hash back to the browser from this route.
- Keep the success response unchanged for normal use.
- Ensure a direct `curl` POST with `password=PlainText123!` results in a bcrypt hash in the database.
- Ensure a direct `curl` POST with only `password3=<anything>` does not write that value.

Attack cases to test:

| Input                                                       | Expected result                                                                         |
| ----------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| `password=ResetMe123!&password2=ResetMe123!`                | Success; DB stores `$2b$12$...`; login works                                            |
| Direct plaintext POST (no `password2`)                      | Success or explicit validation rejection, but never plaintext; document the chosen rule |
| `password=ResetMe123!&password2=different`                  | Rejected; DB unchanged                                                                  |
| `password=`                                                 | Rejected; DB unchanged                                                                  |
| `password` repeated / array / object                        | Rejected as non-string; DB unchanged                                                    |
| `password3=$2b$10$...` with no `password`                   | Rejected; DB unchanged                                                                  |
| Old client body (`password`, `password2`, `password3` hash) | Success; stores hash of `password`, not a hash of `password3`                           |
| 73-byte password (multi-byte UTF-8)                         | Rejected explicitly; DB unchanged                                                       |
| `password="' OR 1=1 --"`                                    | Hashed as data; SQL unaffected (parameterized)                                          |
| Empty token / nonexistent token                             | Existing behaviour; confirm no plaintext write                                          |

Sweep obligation:

- Search the reset path for any other place that writes `users_accounts.password` and report every writer.
- Do not claim the whole application is free of plaintext passwords. Registration still accepts `hashedPassword` from the client; report that as Finding 47.

# 13. Testing Strategy

## Normal case

- Submit matching `password` / `password2`.
- Assert the success string.
- Assert `users_accounts.password` begins with `$2b$12$`.
- Assert `bcrypt.compare(plaintext, stored)` is `true`.
- Log in with the new password.

## Empty / missing input

- Missing `password`.
- Empty `password`.
- Missing `password2` (allowed; still hashes — document the rule).
- Empty token / nonexistent token (existing behaviour; do not fix, but confirm no plaintext write).

## Boundary cases

- Password exactly 72 UTF-8 bytes (accepted).
- Password at 73 UTF-8 bytes (rejected).
- Unicode characters counted by bytes, not code units.
- Password containing `'`, `"`, `--`, `;`.
- `password` as an array or object (form/JSON shape abuse).

## Invalid input

- Confirmation mismatch.
- `password3` only.
- `password3` set to plaintext.
- Non-string values.

## Security cases

- Direct POST with plaintext results in a hash.
- Direct POST with `password3` plaintext/hash does not store it.
- Database and logs do not contain the plaintext.
- Response does not contain the plaintext or hash.
- Hash has cost 12 and a unique salt.
- No double hashing when an old client sends both fields.
- SQL-injection-shaped password is stored as a hash (proves it is data, not SQL).

## Regression testing

- GET `/reset-password/:token` still renders the page with the email.
- Forgot-password flow still creates a token and sends the email (unchanged).
- Login still works with existing cost-10 hashes.
- Login works with a new cost-12 hash.
- Client still redirects to `/login` after success.
- No console errors on the reset page.
- `git diff` shows no changes to unrelated files.

## Manual verification (strongly recommended)
